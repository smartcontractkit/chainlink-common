# commentparsing

Compiles a config struct's doc comments and `validate` tags into the package, so
a consumer in another module can read them without that package's source.

The doc comment on a config field is usually the only description of that field
that exists, and the `validate` tag is usually the only statement that it is
required. Reflection can reach the tag and never the comment, so a tool building
a config reference has to read source — which it cannot do for a dependency.

## How it works

One call, one root value. Nothing else is named:

```go
docs, err := commentparsing.Discover(&Config{})
if err != nil {
    log.Fatal(err)
}
```

`Discover` walks the type tree from that root — through pointers, slices, maps
and embedded fields — and resolves every struct it reaches:

| The type is declared | Where its documentation comes from |
| --- | --- |
| In this module | Parsed from its source, so it cannot disagree with the declaration |
| In a dependency | The `DocComments` method compiled into that package |

The result is the documentation of the whole tree, keyed by type:

```go
docs.Field(reflect.TypeFor[upstream.Retry](), "MaxAttempts").Comment
docs.Type(reflect.TypeFor[Config]())   // every field, or an error if the walk never reached it
docs.Packages()                        // what it found
```

## Generating for the next module down

A dependency cannot be parsed by whoever depends on it, so it compiles its
documentation in. `GenerateDocCommentFiles` writes a file into every discovered
directory this module owns:

```go
//go:generate go run ./gen
```

```go
func main() {
    docs, err := commentparsing.Discover(&Config{})
    if err != nil {
        log.Fatal(err)
    }
    if err := docs.GenerateDocCommentFiles(); err != nil {
        log.Fatal(err)
    }
}
```

That is the whole generator. It takes no arguments and names no packages: the
root type implies them, and each file belongs next to the types it describes
under a fixed name. A config tree spanning three packages of this module gets
three files from one call.

A dependency's package is never written to — its source is in the read-only
module cache, and its documentation is its own repository's to generate.

The output:

```go
// Code generated by github.com/smartcontractkit/chainlink-common/x/config/commentparsing. DO NOT EDIT.

package upstream

import "github.com/smartcontractkit/chainlink-common/x/config/commentparsing"

func (Retry) DocComments() (string, map[string]commentparsing.FieldDoc) {
	return "Retry", map[string]commentparsing.FieldDoc{
		"MaxAttempts": {
			Comment:  "MaxAttempts is the total tries, including the first.",
			Validate: "gte=1",
		},
	}
}
```

## These files are generated — do not edit them

The **single source of truth is the Go doc comment on each field**. To change
what a field's documentation says, edit the comment, then:

```bash
go generate ./...
```

Because the generated file is an artifact, it can fall behind the comments it was
read from. A package that ships one should regenerate in CI and fail on a diff,
the way any other generated file is guarded. Regenerating an unchanged package
produces byte-identical output, so that diff is reliable.

## What it captures

| In the struct | In the generated method |
| --- | --- |
| A field's doc comment | `Comment`, every line of it, not just the first sentence |
| A trailing `// comment` | `Comment`, when there is nothing above the field |
| A `validate` tag | `Validate`, verbatim |
| An embedded field | An entry under the embedded type's own name |

`FieldDoc` is a struct rather than a bare string so that adding to it later —
whether a value is a default or an example, a deprecation note — does not break
the signature every generated file already implements.

A struct with no comment and no tag on any field is skipped: it is some internal
type, and a lookup succeeding on it would be misleading.

## A dependency that never generated is named

A generator run covers only the packages of the module it runs in, so nothing
can promise that a dependency generated too. `Discover` reports that gap instead
of documenting those fields as blank:

```
example.com/upstream.Retry has no DocComments method:
  run `go generate` in the package that declares it
```

Embedding is the sharp edge. A struct that embeds a documented type **promotes
that type's method**, so an ungenerated outer struct would answer `DocComments`
with the embed's fields and no hint that its own are missing. Two things prevent
it: the generated method returns the name of the type it was generated for, and
the lookup checks that against the type it asked about:

```
main.Config promotes DocComments from embedded Settings, so its own fields are
  undocumented: run `go generate` in the package that declares it
```

Any struct with an embedded field therefore qualifies for generation, even one
that adds nothing of its own.

## Why each package generates, instead of finding its source with the go tool

`go list -f '{{.Dir}}' <import path>` resolves any package's directory,
including a dependency's in the module cache at the exact version in play. A
consumer could call that and parse the source itself — no cooperation from the
dependency, no generated files anywhere. We chose generation.

- **It keeps reading documentation a library operation, not a build step.** No
  subprocess, no Go toolchain in the environment, no module cache. A running
  service can describe its own configuration; a stripped container image has no
  SDK to shell out to.
- **`go list` needs a resolvable module graph.** In a hermetic build, a cold
  cache, or a sandbox without network, what should be a directory read becomes a
  download — or a failure.
- **A dependency knows its own types; a consumer guesses.** Whether a nested
  struct is a documented config section or an internal detail is a judgement
  belonging to the package that declares it, and generation puts it there.
- **The failure is legible.** A package that has not generated is named, with the
  fix. A path resolved by string manipulation is not: a config field whose type
  lives in another module fails as `lstat …: no such file or directory` for a
  path nobody wrote.

The cost is real and worth stating: the generated file is an artifact that can
drift, every package on the path has to opt in, and nothing verifies from the
outside that a dependency regenerated. Parsing source has none of those
problems — it just cannot reach a dependency at all.

## Limits

- Only non-test files are read. A config struct declared in a `_test.go` file is
  not part of the package a consumer imports.
- The generated file is skipped when parsing, so regenerating reads the same
  sources as the first run.
- A package that stops documenting anything has its generated file removed, since
  one left behind would answer for types that no longer exist. A hand-written
  file under that name is left alone.

## Examples

| Directory | Shows |
| --- | --- |
| `examples/simple` | One package, one config struct |
| `examples/nested` | Two packages of one module — `Discover` reaches the second through an embed, and one call generates both files |
| `examples/separate_module_use` | A real module boundary — the consumer reads the dependency's documentation without its source |

Each commits its `doccomments_gen.go`, so the generated shape is readable
without running anything. The first two regenerate with:

```bash
go generate ./...
```

`separate_module_use` is two modules of its own, so that command skips it —
`go generate ./...` never descends into a nested module. Its own directive
generates the dependency module first:

```bash
cd examples/separate_module_use && go generate ./...
```

Both of its `go.mod` files carry `replace` directives only because the example
sits inside this repository. A real consumer requires released versions and
needs neither.
