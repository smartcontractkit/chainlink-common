# commentparsing

Recovers a config tree's doc comments from source and feeds them to code
generators, including a built-in one that compiles them into the package so a
consumer in another module can read them back.

A doc comment is the one thing about a field that compilation discards. A struct
tag survives into the type, so anything holding the type reads `validate` and
the rest by reflection — that is why only the comment is carried here.

## How it works

One root value. Nothing else is named:

```go
//go:generate go run ./gen
```

```go
func main() {
	if err := commentparsing.Run(commentparsing.RunArgs{
		Roots:       []any{&Config{}},
		Tool:        "example.com/app/gen",
		LocalPrefix: "example.com",
	}); err != nil {
		log.Fatal(err)
	}
}
```

`Run` walks the type tree from those roots — through pointers, slices, maps and
embedded fields — resolves every struct it reaches, and writes the `DocComments`
methods:

| The type is declared | Where its documentation comes from |
| --- | --- |
| In this module | Parsed from its source, so it cannot disagree with the declaration |
| In a dependency | The `DocComments` method compiled into that package |

A config tree spanning three local packages gets three files from that one call.
A dependency's package is never written to — its source is in the read-only
module cache, and its documentation is its own repository's to generate.

List every type a consumer may reach on its own, not just the outermost config.
A package exposing a config and a secrets file, or two sections meant to be
embedded independently, needs all of them as roots; a section reachable from
none is undocumented for whoever embeds it next.

## Building something else from the same comments

`Run` takes any number of generators, each handed the packages it discovered:

```go
type Generator func(pkgs []Package) (map[string]string, error)
```

A plain function, since there is one thing to do and it is done once — pass a
function, or a method value if your generator carries settings:

```go
commentparsing.Run(args, myReference, (&tomlDocs{Dir: "docs/config"}).Generate)
```

A `Package` carries its import path, package clause, directory relative to the
run directory, and the types the walk reached with their field comments — so a
repository can build a TOML reference, a JSON schema or a settings page from
them without re-implementing the walk or the parsing. Comments arrive already
resolved, whether they came from local source or a dependency's compiled
methods.

Return paths relative to `RunArgs.Dir`. Every generator's files are written in
one pass through `chainlink-common/pkg/utils/codegen`, so formatting, import
grouping and the generated-by header are applied identically to all of them. Two
generators claiming one path is an error rather than a coin toss.

`Files` is `Run` without the writing, returning the same map:

```go
func Files(args RunArgs, generators ...Generator) (map[string]string, error)
func Run(args RunArgs, generators ...Generator) error   // Files, then write
```

Use it when the output has to be inspected before it lands — checking committed
files are up to date, say, which must not write the answer it is about to
compare against. Note that formatting and the header are applied by the write, so
bytes from `Files` are pre-`gofmt`.

`RunArgs.Dir` anchors the run: the module enclosing it decides which types are
local, and it is what generated paths resolve against. Empty means the working
directory, which is where `go generate` starts.

## What a generated file looks like

```go
// Code generated by example.com/app/gen, DO NOT EDIT.

package upstream

import "github.com/smartcontractkit/chainlink-common/x/config/commentparsing"

func (Retry) DocComments() (string, map[string]commentparsing.FieldDoc) {
	return "Retry", map[string]commentparsing.FieldDoc{
		"MaxAttempts": {Comment: "MaxAttempts is the total tries, including the first."},
	}
}
```

## These files are generated — do not edit them

The **single source of truth is the Go doc comment on each field**. To change
what a field's documentation says, edit the comment, then:

```bash
go generate ./...
```

Because the generated file is an artifact, it can fall behind the comments it was
read from, so every generated file needs a `//go:generate` directive reaching it.
This repository's CI runs `make generate` and fails on any resulting diff, which
covers nested modules too — so a directive is all a package has to supply, and a
generated file with none is the one thing that will go unnoticed.

Regenerating an unchanged package produces byte-identical output, which is what
makes that diff meaningful. A generator you add has to hold up its end: sort
anything you iterate out of a map, or it will report a change on every run.

## What it captures

| In the struct | In the generated method |
| --- | --- |
| A field's doc comment | `Comment`, every line of it, not just the first sentence |
| A trailing `// comment` | `Comment`, when there is nothing above the field |
| An embedded field | An entry under the embedded type's own name |
| A struct tag | Nothing — it survives compilation, so reflection reads it off the type |

`FieldDoc` is a struct rather than a bare string because the next thing worth
recording — whether a value is a default or an example, a deprecation note — is
also lost at compile time, and adding it there leaves every generated method's
signature alone.

Only the types the walk reached are carried, so a package's internal structs are
not handed to a generator that would have no idea which of them a config file
can name. Types decoded from a single string, such as a timestamp or a duration,
are left out: they are leaf values, and a dependency has every right to document
no fields on one.

## Using it from another module

A consumer in its own module needs the dependency to have generated, and nothing
else. Require this module and walk your own config:

```go
import "github.com/smartcontractkit/chainlink-common/x/config/commentparsing"

pkgs, err := commentparsing.Discover(moduleRoot, &Config{})
```

Types your module declares are parsed from source. Types from a dependency come
from its compiled `DocComments`, so you need no access to its source tree and no
`go list` to find one — which is what makes this work at all, since a
dependency's source lives in the read-only module cache.

`GenerateDocCommentFiles` only ever writes into directories your own module owns,
so running a generator never tries to modify a dependency.

While the library is unreleased, point at a checkout with a `replace`:

```
require github.com/smartcontractkit/chainlink-common/x/config v0.0.0

replace github.com/smartcontractkit/chainlink-common/x/config => ../chainlink-common/x/config
```

chainlink-ccv's `tools/configdoc` consumes it this way. Its own public API is
unchanged: `Target`, `Main`, `Generator.Write` and `Generator.Check` all behave
as before, with `Generator.Files` exposing the rendering as a [Generator] so one
discovery walk can feed the TOML reference and anything else a repository wants
built from the same comments.

Two things that swap bought it: doc comments for a config field whose type lives
in another module became reachable at all, and a **tagged embedded field's
comment stopped being silently dropped** — `*AWSKMSConfig \`toml:"aws"\`` had no
documentation in the committed output before.

## A dependency that never generated is named

A generator run covers only the packages of the module it runs in, so nothing
can promise that a dependency generated too. `Discover` reports that gap instead
of documenting those fields as blank:

```
example.com/upstream.Retry has no DocComments method:
  run `go generate` in the package that declares it
```

Embedding is the sharp edge. A struct that embeds a documented type **promotes
that type's method**, so an ungenerated outer struct would answer `DocComments`
with the embed's fields and no hint that its own are missing. Two things prevent
it: the generated method returns the name of the type it was generated for, and
the lookup checks that against the type it asked about:

```
main.Config promotes DocComments from embedded Settings, so its own fields are
  undocumented: run `go generate` in the package that declares it
```

Any struct with an embedded field therefore qualifies for generation, even one
that adds nothing of its own.

## Why each package generates, instead of finding its source with the go tool

`go list -f '{{.Dir}}' <import path>` resolves any package's directory,
including a dependency's in the module cache at the exact version in play. A
consumer could call that and parse the source itself — no cooperation from the
dependency, no generated files anywhere. We chose generation.

- **It keeps reading documentation a library operation, not a build step.** No
  subprocess, no Go toolchain in the environment, no module cache. A running
  service can describe its own configuration; a stripped container image has no
  SDK to shell out to.
- **`go list` needs a resolvable module graph.** In a hermetic build, a cold
  cache, or a sandbox without network, what should be a directory read becomes a
  download — or a failure.
- **A dependency knows its own types; a consumer guesses.** Whether a nested
  struct is a documented config section or an internal detail is a judgement
  belonging to the package that declares it, and generation puts it there.
- **The failure is legible.** A package that has not generated is named, with the
  fix. A path resolved by string manipulation is not: a config field whose type
  lives in another module fails as `lstat …: no such file or directory` for a
  path nobody wrote.

The cost is real and worth stating: the generated file is an artifact that can
drift, every package on the path has to opt in, and nothing verifies from the
outside that a dependency regenerated. Parsing source has none of those
problems — it just cannot reach a dependency at all.

## Limits

- Only non-test files are read. A config struct declared in a `_test.go` file is
  not part of the package a consumer imports.
- The generated file is skipped when parsing, so regenerating reads the same
  sources as the first run.
- A package that stops documenting anything has its generated file removed, since
  one left behind would answer for types that no longer exist. A hand-written
  file under that name is left alone.

## Examples

| Directory | Shows |
| --- | --- |
| `examples/simple` | One package, one config struct |
| `examples/nested` | Two packages of one module — `Discover` reaches the second through an embed, and one call generates both files |
| `examples/separate_module_use` | A real module boundary — the consumer reads the dependency's documentation without its source |

Each commits its `doccomments_gen.go`, so the generated shape is readable
without running anything. The first two regenerate with:

```bash
go generate ./...
```

`separate_module_use` is two modules of its own, so that command skips it —
`go generate ./...` never descends into a nested module. Its own directive
generates the dependency module first:

```bash
cd examples/separate_module_use && go generate ./...
```

Both of its `go.mod` files carry `replace` directives only because the example
sits inside this repository. A real consumer requires released versions and
needs neither.
