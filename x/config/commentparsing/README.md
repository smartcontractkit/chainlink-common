# commentparsing

Carries a config struct's doc comments into the compiled package, so they can be read back at run
time — including from another module, whose source is in the read-only module cache.

A doc comment is the one thing about a field that compilation discards. A struct tag survives, so
reflection already reads `validate` and the rest off the type.

API reference: `go doc github.com/smartcontractkit/chainlink-common/x/config/commentparsing`.
Whole working commands: [`examples/`](examples).

## Generate

Add a `//go:generate` directive and a `gen` command to the package declaring your config:

```go
//go:generate go run ./gen

func main() {
	if err := commentparsing.Run(commentparsing.RunArgs{
		Roots:       []any{&Config{}},
		Tool:        "example.com/app/gen",
		LocalPrefix: "example.com",
	}); err != nil {
		log.Fatal(err)
	}
}
```

`Run` walks the type tree from those roots — through pointers, slices, maps and embedded fields —
and writes a `doccomments_gen.go` into every package of your module it reaches. One call covers a
config tree spanning several packages. Commit the generated files.

List every type a consumer may reach on its own, not just the outermost config. A package exposing
a config and a secrets file, or two sections meant to be embedded independently, needs all of them
as roots.

See [`examples/simple`](examples/simple) for the smallest whole version of this.

## Read it back

```go
fields, err := commentparsing.Lookup(reflect.TypeFor[simple.Config]())
fmt.Println(fields["Timeout"].Comment)
```

No source, no Go toolchain, no module cache — the comments are compiled in. A type from a
dependency reads the same way, as long as that dependency generated. If it did not, `Lookup` names
it and says where to run `go generate`.

## Generating something else from the same comments

`Run` takes any number of extra generators, each handed the packages it discovered:

```go
commentparsing.Run(args, myJSONSchema, (&tomlDocs{Dir: "docs/config"}).Generate)
```

A `Package` carries its import path, package clause, directory and the types the walk reached with
their field comments, so a TOML reference or a settings page needs neither the walk nor the
parsing. Comments arrive resolved, whether they came from local source or a dependency's compiled
methods.

`Files` is `Run` without the writing, for a caller that must inspect the output before it lands —
a check that committed files are up to date, say.

## Examples

| Directory | Shows |
| --- | --- |
| [`examples/simple`](examples/simple) | One package, one config struct |
| [`examples/nested`](examples/nested) | Two packages of one module, reached through an embed, generated by one call |
| [`examples/separate_module_use`](examples/separate_module_use) | A real module boundary — the consumer reads the dependency's documentation without its source |

Each commits its `doccomments_gen.go`, so the output is readable without running anything. The
first two regenerate with `go generate ./...` from this directory.

`separate_module_use` is two modules of its own, and `go generate ./...` never descends into a
nested module, so it needs its own invocation:

```bash
cd examples/separate_module_use && go generate ./...
```

Its `replace` directives exist only because it sits inside this repository. A real consumer
requires released versions and needs neither.

## Keeping generated files fresh

The source of truth is the doc comment. To change what a field's documentation says, edit the
comment and re-run `go generate`.

Generated files are artifacts, so they can fall behind. Every one needs a `//go:generate` directive
reaching it; CI runs `make generate` and fails on any resulting diff. Regenerating an unchanged
package produces byte-identical output, which is what makes that diff mean something — a generator
you add has to sort anything it iterates out of a map.

Deleting a documented type is the one edit that needs a hand: the committed file still declares a
method on it, so the package no longer compiles, and a `go run ./gen` that imports that package to
name its roots cannot start — the cleanup below never gets the chance to run. Delete the stale
`doccomments_gen.go` (or have the generate recipe `rm` the artifacts first, as one would for any
generated Go that its own generator imports) and regenerate.

A package that stops documenting anything has its generated file removed, so no committed file
keeps methods for types the tree no longer reaches. Removal is limited to files the same `Tool`
wrote, and to the module being generated: another tool's file, and a nested module's, belong to
their own runs. A file under the reserved name with no generated-by header at all is never written
over — the run fails and names it.

Only non-test files are read, and only those the build in hand selects, as `go build` selects
them.

## Known limitations

**A config type has to exist on every platform that compiles its package.** The file generation
writes carries no build constraint of its own, while the source it reads is filtered by the
build that ran it. A type declared only in `config_linux.go` is therefore missed by a run on
another platform, and given a receiver those platforms cannot compile by a run on Linux. Same for
a type behind a `-tags` build tag, which is not visible to the generator at all. Supporting one
would mean generating per platform and tagging each file, which no config struct here has asked
for; declare config types unconditionally.

**`DocComments` is reserved on a documented type.** A field or hand-written method of that name
cannot coexist with the generated one, so it is reported rather than redeclared.

**A generic type cannot be documented.** A method on its declaration needs a receiver type
parameter list, which the reflected type a run starts from cannot supply. Reported, not generated.

## Why generation, rather than finding a dependency's source with the go tool

`go list -f '{{.Dir}}' <import path>` resolves any package's directory, including a dependency's in
the module cache. A consumer could call that and parse the source itself. We chose generation
because:

- It keeps reading documentation a library operation, not a build step. A running service can
  describe its own configuration; a stripped container image has no Go toolchain to shell out to.
- `go list` needs a resolvable module graph. On a cold cache or in a sandbox without network, a
  directory read becomes a download, or a failure.
- Whether a nested struct is a config section or an internal detail is a judgement belonging to the
  package that declares it.
- A package that has not generated is named, with the fix. A path resolved by string manipulation
  fails as `lstat …: no such file or directory` for a path nobody wrote.

The cost: the generated file can drift, every package on the path has to opt in, and nothing
verifies from outside that a dependency regenerated.
